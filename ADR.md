# Architecture Decision Records

## 1. Backend language and framework: Python + Flask
Date: 2026-10-05
Status: Decided
Context: I needed to pick a language and framework for a small web app with two parts (tickets and check-in), one SQLite database and a few simple pages. It has to start with one command, and I have to be able to explain all of the code myself in the comprehension check.
Decision: I went with Python and Flask, because Python is the language I'm most comfortable with. I use Python's built-in `sqlite3` module to talk to the database and Jinja templates for the pages.
Alternatives considered: Django, but it comes with a lot of things I don't need (an admin panel, its own way of handling the database, a fixed project structure), and the assignment says picking it without a reason counts as poor judgement. FastAPI, but it's mainly good for building APIs and fast async apps, and my app is just a few HTML pages with not much traffic. I also looked at SQLAlchemy for the database, but writing plain SQL means I can see exactly what's happening and explain it more easily.
Consequences: The project stays small and easy to follow, with only a few packages. The downside is that I have to write the SQL myself, and if I change the database structure later there's no automatic tool to update it.

## 2. Keeping tickets and check-in separate so they can be split later
Date: 2026-10-09
Status: Decided
Context: My app has two parts: tickets (organisers create events and sell tickets) and check-in (volunteers let people in at the door). For now they run in one app, but in Assignment 2 they need to become separate services, so I have to decide now where the line between them goes and what is allowed to cross it.
Decision: Each part has its own folder (`tickets/` and `checkin/`) and its own tables. Check-in never imports any tickets code and never reads the tickets or events tables. The only thing that crosses the line is one question, `validate(code, event_id)`, which is passed into `check_in()` and answers "valid", "cancelled", "wrong_event" or "unknown". Things like the number of tickets sold are also passed in instead of looked up.
Alternatives considered: Letting check-in import the tickets service or query the tickets table directly. That would be quicker to write, but then check-in would depend on how tickets stores its data, and splitting them later would mean rewriting check-in. I also thought about one shared module for both parts, but then there would be no clear line to cut along.
Consequences: In Assignment 2, the only change in check-in is that `validate` becomes a web request to the tickets service instead of a normal function call. It also means I can test check-in on its own with a fake validate function. The downside is a bit of repeated code (the small date helpers exist in both parts) and the app has to pass the validate function in every time.

## 3. No foreign key between the check-in and tickets tables
Date: 2026-10-07
Status: Decided
Context: The tickets part of the app owns the `events` and `tickets` tables, and the check-in part owns the `check_ins` table. Check-in needs to know which ticket was scanned, but in Assignment 2 the two parts should be able to become separate services, each with its own database.
Decision: Inside the tickets part, `tickets.event_id` is a normal foreign key to `events`, since both tables belong together. But `check_ins` just stores the ticket code and event id as plain values, with no link to the tickets table. I also made `ticket_code` UNIQUE in `check_ins`, so the same ticket can't be checked in twice.
Alternatives considered: Linking `check_ins` to `tickets` with a foreign key. I didn't do this because it would tie the two parts together in the database, and splitting them later would mean redesigning the tables. I also thought about stopping double entry with an "already used?" check in Python before saving, but if two volunteers scan the same ticket at the exact same moment, both checks could pass. With UNIQUE, the database itself refuses the second one.
Consequences: Check-in can move to its own database later without changing its table. The downside is that the database won't stop a fake ticket code from being saved, so the check-in code always has to ask the tickets part with `validate_ticket(code, event_id)` first.

## 4. Testing approach: business rules first, then the main user flows
Date: 2026-10-10
Status: Decided
Context: The assignment asks for at least 70% coverage on the core business logic of both parts. I had limited time, so I had to decide what was most important to test and what could stay thinner.
Decision: Most of my tests are on the business rules in `tickets/service.py` and `checkin/service.py`, because that's where mistakes would really hurt (selling more tickets than seats, letting someone in twice). Each of those tests gets a fresh database in memory and passes the time in itself, so results never depend on the clock. Check-in is tested with a fake validate function, so it's tested without the tickets part. After that I added page tests with Flask's test client for the main flows, like selling a ticket and then checking it in at the door. I run them with `pytest --cov=tickets --cov=checkin --cov-report=term-missing`, which gives about 96% overall.
Alternatives considered: Testing mostly through the pages. That would cover more code per test, but when something fails it's harder to see which rule broke, and every rule would need a full page request. I also thought about browser tests (like Selenium), but that's a lot of setup for a few simple HTML pages.
Consequences: The rules are tested well and the tests run fast. Thinner parts: some rare error paths in the pages (like a missing name when selling), how the pages look, two people buying the last ticket at the exact same moment (I only checked that once by hand), and the Docker container, which is checked by the provided `run.sh` instead of pytest.

## 5. Not building QR code scanning at the door
Date: 2026-10-12
Status: Decided
Context: At the door, volunteers need to check tickets quickly. The obvious way would be to show a QR code on each ticket and scan it with a phone camera, and I had it in my original plan.
Decision: I didn't build QR codes. Volunteers type the ticket code into a big input box on the door page instead.
Alternatives considered: Scanning QR codes with the phone camera. That needs JavaScript in the browser, a camera permission, a scanning library and testing on different phones, which is a lot of extra work and risk for this assignment. Only showing a QR code on the ticket would also need an extra package, and it doesn't help without a scanner. Typing the code still tests all the important logic: is the ticket valid, and has it already been used.
Consequences: Checking people in is slower, and typing mistakes are possible (they show up as "Unknown ticket code", so nobody gets in by mistake). QR could be added later without changing the database or the check-in logic, because the QR code would just contain the same ticket code.


## 6. Check-in asks the tickets service over HTTP, with a timeout and a fallback
Date: 2026-11-19
Status: Decided
Context: In Assignment 2 the app became two services, tickets and check-in, each with its own container and its own database. Check-in still needs to know if a scanned ticket is valid for the event, and the report needs the number of tickets sold. Since ADR-2 the only thing allowed to cross the line was `validate(code, event_id)`, but now that question has to travel between two separate containers, and the tickets service might be slow or down.
Decision: Check-in calls the tickets service's JSON API over HTTP, through one small file, `tickets_client.py`: `GET /tickets/{code}/validate?event_id=...` for a scan and `GET /events/{id}` for the report. The address comes from `TICKETS_URL` (in compose it is `http://tickets:8000`, found by the service name), and every call has a timeout of `TICKETS_TIMEOUT_S` (2 seconds). If tickets doesn't answer in time or returns an error, the scan is refused with 503 and a clear message instead of letting someone in without a check, and the report still shows check-in's own numbers (how many people came in) with a note that the tickets numbers are missing. Check-in never connects to the tickets database.
Alternatives considered: Letting check-in read the tickets database directly. It would be faster and keep working when the tickets service is down, but it breaks the "own database per service" rule, and any change to the tickets tables could break check-in. A message queue, where tickets sends events like "ticket cancelled" and check-in keeps its own copy, would also survive tickets being down, but it needs a third piece of infrastructure, and a cancelled ticket could still get in if the message arrived late. For one call per scan, plain HTTP is enough.
Consequences: The two services only depend on each other through two documented endpoints, so either one can change its database or code freely. The downside is that check-in can't let anyone in while tickets is down, which is the safe choice for an event (better a short queue at the door than letting in cancelled tickets). Each scan also waits for a network call, which is fine at door speed. The timeout makes sure a stuck tickets service makes check-in fail fast instead of hanging.

## 7. One SQL Server database per service, changed only through versioned migrations
Date: 2026-11-20
Status: Decided
Context: In Assignment 1 the app used one SQLite file, created from schema.sql on startup. After the split into two services (ADR-6), each service needs its own data, and on Azure the containers can be restarted or replaced at any time, so a file inside the container would be lost. I also need a safe way to change the tables later without losing the data that is already there.
Decision: Each service has its own SQL Server database and its own login, which only has rights on that database (locally both databases run in one SQL Server container, on Azure they are two Azure SQL databases). The connection string comes from `DATABASE_URL`, so the code doesn't know if it's local or Azure. The tables are created and changed only through numbered files in `migrations/` (001_init.sql, 002_..., and so on). When a service starts, migrate.py looks in its `schema_migrations` table, runs every file that hasn't been applied yet in order, each in its own transaction, and writes it down. Migrations only go forward: a file that was applied is never edited, a change is always a new file. Tests run the same migrations on a separate test database.
Alternatives considered: Keeping SQLite with the file on an Azure file share. It would mean almost no code changes, but SQLite doesn't handle a network share well (locking problems) and it can't be shared safely if a service ever runs with two copies. One shared database for both services, which is simpler and cheaper, but then check-in could read the tickets tables directly and the line between the services from ADR-2 and ADR-3 would be gone. A migration tool like Alembic, which can also go back down, but it needs SQLAlchemy models, and my code uses plain SQL (ADR-1); a small script of about 50 lines does what I need and I can explain every line.
Consequences: Each service owns its data and can change its tables without asking the other one. Every database, local, CI or Azure, is built the same way from the same files, and I can see exactly which changes have been applied. The downsides: SQL Server needed some changes to my SQL (OUTPUT INSERTED.id instead of lastrowid, UPDLOCK instead of BEGIN IMMEDIATE, a binary collation so ticket codes stay case-sensitive), it is heavier to run locally than a file, and because there is no "down", undoing a mistake means writing another migration.

## 8. Running on Azure: Container Apps that scale to zero, serverless SQL and a static website
Date: 2026-11-21
Status: Decided
Context: The system has to run on Azure in my Azure for Students subscription, which has $100 of credit and only allows five regions. It must have a public HTTPS address, be deployed only by the pipeline, and cost almost nothing when nobody uses it. The two services are containers, each with its own database (ADR-7), and the UI is just static files.
Decision: Everything is in one resource group in germanywestcentral. Each service is an Azure Container App with external HTTPS ingress and 0 to 1 replicas, so it scales to zero when idle and doesn't use credit. Both apps share one Container Apps environment, whose logs go to a Log Analytics workspace. The data is in one Azure SQL server with one serverless database per service on the free offer, which pauses after 60 minutes without use. The UI is a Storage static website, which is cheap and gives the public address, and it is the only origin the services allow (CORS in the code through UI_ORIGIN, because the Container Apps CORS setting blocks POST requests). GitHub Actions signs in as a managed identity through OIDC, which only has Contributor on this resource group, so no Azure password is stored anywhere. Database passwords are GitHub secrets that CD puts into each app as a Container Apps secret. After the one-time setup in the README, only the pipeline changes anything.
Alternatives considered: Azure App Service, which is simpler for web apps, but its plans keep running and cost money even when idle, and it doesn't scale to zero. Azure Kubernetes Service, which is far too much to set up and run for two small containers. Running SQL Server as another container next to the services, which would be free, but data in a container is lost when it restarts and there are no backups. A Static Web App for the UI, but the assignment asks for a storage static website. A service principal with a client secret for the pipeline, but IE accounts can't create one, and a secret that never expires is riskier than OIDC tokens that only work for pushes to main of my repository.
Consequences: An idle system costs almost nothing, and each part can be checked and redeployed on its own. Every deploy is traceable to a commit, because the image tag and /health both show the SHA. The price is cold starts: after a quiet period the first request can take about a minute while the container starts and the database resumes, so the services retry the database connection with backoff and the UI shows a "starting up" message and retries reads. With at most one replica there is no redundancy, which is acceptable for a student project but not for a real event with thousands of people at the door.

## 9. The pipeline: four checks before any image is built, and every merge to main is deployed
Date: 2026-11-22
Status: Decided
Context: After the split, a change can break one service, the seam between them, the description of the system or the deployment, and nobody should have to remember to check all of that by hand. Branches go through pull requests, and main is deployed to Azure automatically (ADR-8), so anything merged must already be proven to work.
Decision: ci.yml runs on every pull request and every push to a branch, and cd.yml calls it on main. It has four checks that must all pass before any image is built: test (each service's unit tests against a real SQL Server in a throwaway container, coverage at least 70%), system (system.yaml against the professor's schema and against the code, plus both OpenAPI files), lint (ruff for real mistakes like unused or undefined names and likely bugs), and integration (both real services and SQL Server started with docker compose, then tests across the seam: a check-in that goes through the tickets service, a ticket cancelled in tickets being refused at the door, the combined report, and then the same with the tickets service stopped, where check-in must answer 503 quickly and the report must degrade). Images are tagged with the commit SHA and only pushed on main, then cd.yml deploys exactly that SHA and fails unless both /health endpoints return 200.
Alternatives considered: Only unit tests with a fake tickets service. They are fast and already exist, but they can't catch a mistake in the HTTP call itself (a wrong URL, a wrong field name), which is the most likely place for the split to break. Testing against SQLite in CI instead of SQL Server, which is faster, but SQL Server behaves differently (case-insensitive text, locking), so tests could pass and the real database could still fail. Deploying by hand when I think it's ready, which is simpler, but then what runs on Azure may not be what is in main.
Consequences: Main is always tested and deployed, and every running version can be traced to one commit. The cost is time: a CI run takes a few minutes because SQL Server has to start in three jobs, and the integration job depends on Docker images being available. The integration tests share one database in order (they create an event, then check in), so they are slower to debug than unit tests when one fails.
